title: "Instana"
---

OpenSRE talks to Instana's REST API directly to investigate incidents: events,
golden-signal metrics, slow/erroring traces, infrastructure, AWS resource
mapping, and — most importantly — the actual exception text behind a service's
errors.

## Tools

| Tool | What it does |
| --- | --- |
| `instana_get_events` | List significant Instana events/incidents in a window (ranked, with totals). Excludes infra `change`-type noise by default — pass `include_changes=true` to include them. |
| `instana_get_event_detail` | Fetch one event by id or event URL. |
| `instana_application_metrics` | Golden-signal metrics (latency, error rate, throughput) for a service. |
| `instana_infrastructure_health` | Query hosts/containers/pods and their health. |
| `instana_traces` | Slowest traces for a service (latency desc). For error-rate incidents, pass `erroneous_only=true` to get the actual failing traces. |
| `instana_get_trace_detail` | Spans of one trace, ranked by duration, with downstream service/endpoint and error count. |
| `instana_error_analysis` | The real exception messages behind a service's errors, ranked by count (and which services error most). |
| `instana_get_investigation_context` | One-shot RCA bundle: events + metrics + slowest traces + top error messages. |
| `instana_get_application_context` | Resolve an Instana Application Perspective by name to its member services and which of them are erroring most. Call this first for application-scoped alerts, then drill into the returned services. |
| `instana_resolve_aws_resource` | Map an Instana AWS entity (snapshotId) to its AWS account/region/ARN. |
| `instana_search_logs` | Search Instana logs (requires Instana Log Management; returns unavailable on APM-only tenants). |

All query tools accept an optional `to_ms` (epoch milliseconds) to anchor the
lookback window to the event's end time instead of "now" — pass it to
investigate a past/closed incident within the window it actually occurred in. Without
`to_ms` the window ends at the current time.

## Application-perspective alerts

An Instana Smart Alert can fire on an **Application Perspective** — a named group
of services — rather than a single service. The alert's name is the application,
not something you can query as a `service_name`. For those, call
`instana_get_application_context(application="<name>")` first: it resolves the
application to its member services and ranks which of them are erroring most, so
you can drill into the real failing service with
`instana_get_investigation_context` / `instana_error_analysis` instead of
querying the application name as if it were a service.

## Configuration

Set two values for your Instana integration:

| Key | What it is |
| --- | --- |
| `INSTANA_BASE_URL` | Your Instana tenant URL, e.g. `https://apm-acme.instana.io`. |
| `INSTANA_API_TOKEN` | An Instana API token with read access. |

## Naming the root cause

`instana_error_analysis` is the primary signal for naming a real root cause. It
returns the actual exception strings Instana recorded for erroring calls —
application errors and downstream database errors alike — ranked by how often
they occurred, rather than just an error count.

```text
You: why is tiam-ms-profile erroring?

instana_error_analysis(service_name="tiam-ms-profile")
→ error_messages:
    - "NOT_FOUND: National ID not found"        count: 7702
    - "FAILED_PRECONDITION: duplicate request"  count: 33
```

Called without a `service_name`, it also returns which services are erroring most
across the system:

```text
instana_error_analysis()
→ top_services:
    - catalog          count: 4498
    - tiam-ms-profile  count: 803
```

## A one-shot start

`instana_get_investigation_context` bundles the common starting signals in a
single call — recent events, a golden-signal metric summary, the slowest traces,
and the top real error messages for the service:

```text
instana_get_investigation_context(service_name="catalog")
→ events, metrics, slowest_traces, error_messages
```

## Focusing on the right events and traces

By default `instana_get_events` drops `change`-type infrastructure events (host
online/offline churn and similar) so real incidents and issues aren't crowded
out. If you need that infra churn too, pass `include_changes=true`.

For an error-rate incident, `instana_traces(service_name=..., erroneous_only=true)`
returns the traces that actually failed instead of the slowest ones — the slowest
traces are often not the erroring ones, so this lets you drill straight into a
failing request. The default (no `erroneous_only`) still returns the slowest
traces by latency for latency investigations.

## A note on logs

`instana_search_logs` uses Instana Log Management, which is a separately-licensed
capability. On tenants without it (for example, APM-only tenants) every log
endpoint returns 404 and the tool reports `available: false`. In that case the
result is marked non-retryable — don't keep re-calling it — and you should use
`instana_error_analysis` for the real exception text behind a service's errors.
